# 设备管理模块技术架构

## 1. 技术目标

设备管理模块需要提供统一设备模型，屏蔽不同设备类型和协议差异。MVP 阶段以数据库模拟设备为主，后续可接入真实 WiFi、Zigbee、BLE Mesh 网关。

## 2. 分层架构

| 层级 | 职责 |
| :--- | :--- |
| APP 页面层 | 设备列表、添加设备、设备设置、房间管理 |
| APP 状态层 | 当前家庭、房间列表、设备列表、筛选条件 |
| REST API | 设备、房间、设备类型、设备资料维护接口 |
| 设备领域服务 | 设备创建、属性初始化、房间移动、删除关联处理 |
| 模拟设备引擎 | 生成设备默认属性和在线状态 |
| 数据层 | 设备表、房间表、设备属性表、产品类型表 |

## 3. 核心设计

### 3.1 设备产品模型

产品模型用于描述某类设备具备哪些属性和能力。例如灯具具备 `power`、`brightness`、`colorTemp`，空调具备 `mode`、`temperature`、`fanSpeed`。

### 3.2 设备实例模型

设备实例是家庭中的具体设备，归属于某个家庭和房间，关联一个产品类型，并拥有独立状态和属性。

### 3.3 属性存储方案

MVP 可采用 JSON 字段存储设备属性，便于快速扩展不同设备类型。后续如需复杂统计，可拆分为属性明细表或时序数据库。

## 4. API 设计

| 方法 | 路径 | 说明 | 权限 |
| :--- | :--- | :--- | :--- |
| GET | `/api/families/{familyId}/rooms` | 房间列表 | 成员 |
| POST | `/api/families/{familyId}/rooms` | 新增房间 | 管理员 |
| PUT | `/api/rooms/{roomId}` | 修改房间 | 管理员 |
| DELETE | `/api/rooms/{roomId}` | 删除房间 | 管理员 |
| GET | `/api/device-products` | 设备产品类型 | 登录 |
| POST | `/api/families/{familyId}/devices/mock` | 添加模拟设备 | 管理员 |
| GET | `/api/families/{familyId}/devices` | 设备列表 | 成员 |
| GET | `/api/devices/{deviceId}` | 设备详情 | 成员 |
| PUT | `/api/devices/{deviceId}` | 修改设备资料 | 管理员 |
| DELETE | `/api/devices/{deviceId}` | 删除设备 | 管理员 |

## 5. 设备状态字段

| 字段 | 含义 |
| :--- | :--- |
| ONLINE | 在线，可控制 |
| OFFLINE | 离线，不可控制 |
| FAULT | 故障，可查看但不建议控制 |
| PAIRING | 配网中 |
| DELETED | 已删除 |

## 6. 添加设备实现原理

1. 校验当前用户是否为家庭管理员。
2. 校验房间是否属于当前家庭。
3. 查询产品类型默认属性模板。
4. 创建设备实例。
5. 写入设备属性 JSON。
6. 发送设备新增事件。
7. APP 刷新设备列表或通过 WebSocket 接收新增事件。

## 7. 删除设备实现原理

1. 查询设备归属家庭。
2. 校验管理员权限。
3. 查询设备关联的自动化规则和场景。
4. 软删除设备。
5. 停用或标记相关规则。
6. 写操作审计日志。
7. 推送设备删除事件。

## 8. 前端状态管理

- `roomStore`：房间列表、当前选中房间。
- `deviceStore`：设备列表、设备详情、设备筛选条件。
- 进入首页时拉取房间和设备列表。
- WebSocket 收到设备新增、删除、状态变化后局部更新。

## 9. 性能策略

- 首页设备列表分页或按房间懒加载。
- 设备卡片只展示关键属性，详情页再加载完整属性。
- 产品类型列表可长期缓存。
- 房间和设备变更后使用增量事件刷新。

## 10. 测试重点

- 不同角色添加、编辑、删除设备。
- 删除房间时存在设备的拦截逻辑。
- 添加不同类型模拟设备时属性模板是否正确。
- 设备列表按房间和分类筛选是否准确。
